# Практическое занятие: Финальная проверка MVP

## Шаг 1. Контроль соответствия MVP исходным гипотезам

## **Сегмент**: Гости вечеринок и домашних встреч — люди 18–45 лет, участники компаний от 5 до 20 человек 
## **Проблема**: Гости не могут влиять на музыку, испытывают неловкость при просьбах, хост отвлекается от общения 
## **Ценность**:  Возможность добавить свой трек в общую очередь и повлиять на музыку без установки приложений, регистрации и неловких просьб 
## **Целевое действие на MVP**:  Добавление трека в очередь гостем 
## **Что считаем «успехом»**:  70% гостей сканируют QR-код, 40% добавляют хотя бы один трек 

### Ответы на контрольные вопросы

**Каким образом MVP решает заявленную проблему?**
MVP устраняет необходимость кричать через комнату или лично просить хоста. Гость сканирует QR-код, попадает в веб-интерфейс и добавляет свой трек в общую очередь. Лайки позволяют влиять на порядок воспроизведения, а хост освобождается от роли «диджея».

**Соответствует ли продукт первоначальной концепции и гипотезам ЦА?**
Да, MVP полностью соответствует концепции: вход без установки приложений и регистрации, QR-код как точка входа, демократичное голосование. Главная гипотеза («гости готовы сканировать QR-код и добавлять треки») остаётся неизменной и проверяемой.

## Шаг 2. Аудит функциональности и юзабилити

### Таблица функций текущего MVP

| Функция | Категория | Какой шаг сценария обеспечивает | Вклад в ценность | Проблемы / Замечания |
|:---|:---|:---|:---|:---|
| Создание комнаты без регистрации | Core | Вход хоста | Быстрый старт, минимальный барьер | Нет проблем |
| Генерация QR-кода и ссылки | Core | Создание комнаты | Гости подключаются без установки | Нет проблем |
| Подключение по QR-коду | Core | Вход гостя | Нулевой порог входа | Нет проблем |
| Поиск треков в Яндекс.Музыке | Core | Поиск трека | Доступ к любимой музыке | Только один источник |
| Добавление трека в очередь | Core | Добавление трека | Наполнение очереди | Нет проблем |
| Голосование (лайки) | Core | Голосование | Демократия, влияние каждого | Нет проблем |
| Упорядочивание очереди по лайкам | Core | Голосование | Прозрачность, видимость результата | Нет проблем |
| Воспроизведение на устройстве хоста | Core | Получение результата | Физическое звучание через колонку | Зависимость от Web Audio API |
| Отображение текущего трека и очереди | Core | Получение результата | Информированность | Нет проблем |
| Базовый плейлист по умолчанию | Support | Создание комнаты | Решает проблему «холодного старта» | Можно упростить |
| Аватарки/никнеймы гостей | Support | Вход гостя | Социальный аспект | Не критично для MVP |
| Сохранение трека в плейлист | Support | Фиксация результата | Удержание | Перенести в Later |

### Анализ

**Какие фичи можно убрать без потери ценности?**
- Аватарки и никнеймы гостей (не влияют на добавление треков и голосование)
- Сохранение трека в личный плейлист (ценно, но не критично для проверки главной гипотезы)

**Какие фичи стоит упростить?**
- Базовый плейлист по умолчанию — использовать фиксированный короткий плейлист из 5-10 треков вместо алгоритмической подборки
- Поиск треков — ограничиться одним источником (Яндекс.Музыка), без переключения между сервисами

**Какие фичи нужно добавить, если без них ключевой сценарий «ломается»?**
- Обработка ошибки «трек не найден» — уже в плане, но критична для UX
- Индикатор загрузки при поиске — чтобы гость понимал, что система работает

## Шаг 3. Корректировка функциональности

### Убрать / перенести в Later

| Функция | Решение | Обоснование |
|:---|:---|:---|
| Аватарки / никнеймы гостей | Перенести в Later | Не влияет на добавление треков и голосование |
| Сохранение трека в личный плейлист | Перенести в Later | Дополнительная ценность, не критична для проверки гипотезы |

### Упростить

| Функция | Упрощение | Обоснование |
|:---|:---|:---|
| Базовый плейлист по умолчанию | Использовать фиксированный список из 10 популярных треков | Не требует алгоритмов, решает проблему «холодного старта» |
| Поиск треков | Только Яндекс.Музыка, без переключения между сервисами | Снижает сложность интеграции |

### Добавить в Core

| Функция | Обоснование |
|:---|:---|
| Индикатор загрузки при поиске | Без него гость не понимает, идёт поиск или система не отвечает |
| Сообщение об ошибке «трек не найден» | Без понятного сообщения гость может подумать, что сервис не работает |

## Шаг 4. Гипотетическая проверка метрик и воронки

### North Star Metric

**NSM:** Количество успешно добавленных треков на одну активную комнату.

### Воронка взаимодействия

| Шаг воронки | Действие пользователя |
|:---|:---|
| 1 | Сканирование QR-кода |
| 2 | Открытие страницы комнаты |
| 3 | Ввод запроса в поисковую строку |
| 4 | Просмотр результатов поиска |
| 5 | Нажатие кнопки «Добавить» |
| 6 | Появление трека в очереди |
| 7 | (Опционально) Постановка лайка |

### Таблица метрик

| Метрика | Зачем нужна | Как измеряем |
|:---|:---|:---|
| % сканировавших QR-код | Оценить барьер входа | Событие «комната открыта» / количество гостей на вечеринке |
| % добавивших трек | Оценить готовность участвовать | Событие «трек добавлен» / количество гостей в комнате |
| Среднее количество треков на гостя | Оценить вовлечённость | События «трек добавлен» по гостю |
| % лайкнувших хотя бы один трек | Оценить интерес к голосованию | Событие «лайк поставлен» / количество гостей |
| Конверсия из поиска в добавление | Оценить качество поиска | Событие «добавление» / событие «поиск» |

### Ответы на вопросы

**Какие ключевые метрики стоило бы отслеживать?**
% сканировавших QR-код, % добавивших трек, среднее количество треков на гостя, % лайкнувших хотя бы один трек.

**Как можно было бы проверить вовлеченность пользователей?**
По повторным визитам в ту же комнату (возвращение к очереди), по количеству лайков на чужие треки, по времени, проведённому в комнате.

**Как бы выглядела воронка взаимодействия?**
Сканирование QR → открытие комнаты → поиск трека → добавление трека → (лайк). Каждый шаг — потенциальная точка оттока.

## Шаг 5. Подготовка к реальному тестированию (гипотетическое моделирование)

### План пилота

| Параметр | Значение |
|:---|:---|
| **Кого тестируем** | 5–10 организаторов домашних вечеринок из Telegram-чатов и личного окружения |
| **Формат** | Доступ к MVP по ссылке + короткое интервью после использования на реальной вечеринке |
| **Сценарий теста** | 1. Создать комнату<br>2. Показать QR-код гостям<br>3. Гость добавляет трек<br>4. Гость ставит лайк<br>5. Хост запускает воспроизведение<br>6. Завершить комнату |
| **Вопросы** | 1. Что было непонятно?<br>2. Сколько гостей добавили треки?<br>3. Возникали ли технические проблемы?<br>4. Будете ли использовать снова?<br>5. Что улучшить? |
| **Критерии успеха** | 70% гостей сканируют QR-код, 40% добавляют трек, 8 из 10 хостов готовы использовать снова |
| **Критерии провала** | Менее 50% сканируют QR-код, менее 20% добавляют трек, более 3 технических блокирующих проблем |

### Ответы на вопросы

**Какие шаги нужно предпринять для реального тестирования?**
1. Развернуть MVP на публичном сервере.
2. Найти 5–10 организаторов (через Telegram-чаты, личные контакты).
3. Выдать доступ, попросить протестировать на реальной вечеринке.
4. Собрать метрики (аналитика в приложении).
5. Провести интервью после использования.
6. Проанализировать данные и сделать выводы.

**Как бы выглядел процесс сбора обратной связи?**
1. Автоматический сбор событий в аналитике (сканирование, добавление треков, лайки).
2. Опрос в Google Forms после завершения комнаты.
3. Короткое интервью (15 минут) с хостом по телефону/видеозвонку.
4. Фиксация основных проблем и пожеланий в таблицу (Notion/Google Sheets).
